# rhp-builtins file layout

`crates/rhp-builtins/src` follows php-src. A builtin lives in the Rust file
named after the php-src file whose `PHP_FUNCTION` defines it, in the
directory php-src keeps that file in: `zend/` for `Zend/`, `main/` for
`main/`, `ext/<name>/` for `ext/<name>/` and `sapi/` for `sapi/`. To find
where rhp implements a function, look up where php-src defines it.

- A directory module's `mod.rs` is that directory's main file when php-src
  has one: `main/mod.rs` is main/main.c, `main/streams/mod.rs` is
  main/streams/streams.c, `ext/<name>/mod.rs` is the extension's main file.
- A new builtin goes into the file of its php-src file, which is created if
  it does not exist yet, and registers through its php module. Every php
  module is a `ModuleDef` (`module.rs`, php's `zend_module_entry`):
  `registry::modules()` lists Core (zend/ and main/, in `registry.rs`),
  standard (`ext/standard/mod.rs`) and the other extensions (`ext/mod.rs`).
  A module states php's name for it, its functions, constants, prelude
  classes, stream wrappers, its per-request reset (`no_state` when it has
  none) and its object-freed hook (`None` when it keeps nothing by object
  id). The function table, the constants, the prelude, the wrappers, the
  reset and the object free hook are all built from that list.
  The preludes are concatenated into one file; a module whose classes are
  namespaced puts them in `namespace X { ... }` blocks (ext/random).
- A constant is defined once, by the module and file that register it in
  php-src, next to the Rust constant its code uses.
- Helpers stay with their callers. A helper several files call lives where
  php-src keeps its counterpart (`zend/zpp.rs` for argument parsing,
  `main/ini.rs` for ini values).
- Unit tests sit in a sibling `<file>/tests.rs`. A few tests stay in the
  test file whose helpers they use and import the function they test: for
  example `array_is_list`'s test is in `ext/standard/array/tests.rs`,
  `number_format`'s in `string/tests.rs` and the zend `strcmp` family's in
  `string/tests.rs`.

## Files

### Crate files

These have no php-src counterpart.

| file | holds |
|---|---|
| `lib.rs` | the module tree and the crate's public API (re-exports) |
| `registry.rs` (+ `registry/tests.rs`) | the module list and Core's module; the function table, the constant table, the prelude, lookup, and the hooks the engine calls into every module (request reset, object freed, constant deprecation) |
| `host.rs` | the `Host` trait: what builtins may ask of the VM |
| `diag.rs` | `php_error_docref`-style diagnostics (main/main.c's `php_error_docref`) |
| `module.rs` | `ModuleDef` (the role of `zend_module_entry`) and internal output handler aliases |
| `version.rs` | the reference build's identity and library versions (main/php_version.h and configure's values) |
| `const_modules.rs` | generated by `gen dumps`: the reference php's constants by module |
| `func_modules.rs` | generated by `gen dumps`: the reference php's functions by module |
| `core_prelude.php` | Zend's built-in classes and interfaces, in PHP |
| `test_support.rs` | the host the unit tests call builtins with |

### Other extensions

One directory per php-src extension, `ext/<name>/`:

| directory | php-src |
|---|---|
| `ext/json/` | ext/json: json.c, the encoder and the parser |
| `ext/pcre/` | ext/pcre: `mod.rs` is the PCRE2 binding with php_pcre.c's per-thread state, `php_pcre.rs` php_pcre.c's functions |
| `ext/filter/` | ext/filter |
| `ext/opcache/` | ext/opcache's zend_accelerator_module.c; the cache itself is in rhp-vm (`opcache/`) |
| `ext/random/` | ext/random: random.c (`mod.rs`), the engines (`engine.rs`), randomizer.c, gammasection.c and the engines' methods (`randomizer.rs`); the classes in `prelude.php` |
| `ext/readline/` | ext/readline/readline.c |
| `ext/session/` | ext/session: session.c, mod_user.c and mod_user_class.c (`mod.rs`, SessionHandler in `prelude.php`), mod_files.c (`mod_files.rs`); trans-sid goes through `ext/standard/url_scanner_ex.rs` |
| `ext/spl/` | ext/spl: php_spl.c, spl_iterators.c's `iterator_to_array`, the prelude classes |
| `ext/date/` | ext/date: php_date.c over timelib |

The library-backed extensions (bcmath, bz2, ctype, curl, dom, gmp, hash,
iconv, intl, libxml, mbstring, openssl, pcntl, pdo, pdo_sqlite, phar, posix,
reflection,
simplexml, sockets, tokenizer, xml, xmlreader, xmlwriter, zip, zlib) keep
their php-src directory name; libraries.md describes their files.

### sapi/

| file | php-src |
|---|---|
| `sapi/mod.rs` | `SapiDef`: what a SAPI brings besides its callbacks |
| `sapi/cli.rs` | sapi/cli: php-cli's `SapiDef`, php_cli_process_title.c |
| `sapi/cgi.rs` | sapi/cgi/cgi_main.c: php-cgi's `SapiDef` and its `cgi-fcgi` module's `apache_request_headers`, `apache_response_headers`, `apache_child_terminate` |

Each SAPI supplies its own functions: a `SapiDef` names the SAPI, its
`additional_functions` (php files them under `standard`), its own module
and that module's functions (php-cgi's `cgi-fcgi`), whether it loads the
`cli_only` modules (pcntl), and its per-request reset. The registry holds
every SAPI's functions, each marked with the SAPIs that supply it
(`Builtin::sapis`); the running SAPI's name selects its `SapiDef`
(`main::sapi::set_sapi`), and `lookup_lc` finds only that SAPI's. A SAPI
without one (an embedding server) adds nothing. `dl` is in neither: rhp cannot load
php's C extensions. `get_extension_funcs()` lists php's functions of a
module (`func_modules.rs`, generated by `gen dumps`) that rhp has under
the running SAPI, native or in the prelude (`Host::internal_function_exists`);
a user function of the same name does not count.
